# ADR-0011：事件出口——接缝已存在，协议等第一个消费者

- 日期：2026-08-26
- 状态：已接受
- 相关章节：ARCHITECTURE.md §2.3（原则 5：抽象时机）、§2.4（广播站比喻）、§7.3（Observer）、§4.4（EventSink）、§4.9-5（事件投递）

## 背景

对照 gooophira-mp（应用层全家桶：HTTP API/GUI/回放/SQLite 统计/Webhook/Redis 缓存），r0semi 为极致内存只保留纯房间内核。此前讨论提出"事件出口"——把内核事件流导出给外部进程，使应用层全部进程外化、内核保持 7-15MB。**本 ADR 回答前置问题：是否真的需要"事件出口"？需要的话，现在该设计到什么程度？**

## 现状核查（代码事实）

**结论先行："事件出口"的接缝层 100% 已存在，且已有一个非会话消费者证明可行。**

1. **`EventSink` trait**（phira-core/src/bus.rs:45）：`async fn deliver(&self, user_id: i32, event: &RoomEvent)`——事件投递的抽象接缝，core 只认识它，不认识具体消费者。
2. **`CompositeSink`**（phira-server/src/server.rs:284）：`RwLock<Vec<Arc<dyn EventSink>>>` + 组合根注入——**多 sink 扇出已是现状**，不是"阶段 4 待改造"。
3. **两个已存在的消费者**：
   - `SessionSink`：推送模型——`event_to_server` 转换 + `EncodeCache` 编码共享（ADR-0009）→ per-user 会话 channel
   - `RoomListSink`：**拉模型**——事件维护房间列表快照（`HashMap<RoomId, RoomInfo>`），HTTP `/rooms` 端点查询快照
4. **外部进程消费者：0 个**。所有消费者（会话、房间列表）都是进程内的。
5. **阶段 4 的 Observer（§7.3 `Moderator`）是进程内订阅**（命令路径 `intercept` + 事件 `on_event`），不是进程外——封禁/审核/反作弊都不需要"进程外出口"。

## 需求质疑：真的需要"事件出口"吗？

**需要的是"出口"——但出口已经存在（EventSink 接缝 + CompositeSink 扇出）。真正缺失的只有"进程外传输实现"这一个具体实现，而它属于"第二个实现"，现在设计它就是在猜接口（违反原则 5）。**

逐项论证：

| 潜在外部消费者 | 现在需要吗 | 接缝是否够用 |
|---|---|---|
| 管理面板/GUI（房间/玩家状态） | 否 | **够**——`RoomListSink` 已证明"事件维护快照 + HTTP 拉取"模式可行（/rooms 端点） |
| 回放录制（.phirarec） | 否（阶段 4+） | 够——录制消费结构化 `Arc<Vec<TouchFrame>>`，进程内 Observer 即可（§7.3 形态），不必须进程外 |
| 统计/Webhook 通知 | 否 | 够——低频事件，`RoomListSink` 同款模式或未来 Observer |
| 封禁/审核 | 否（阶段 4） | **进程内 Observer**（`intercept` 命令路径否决），明确不需要进程外 |

**关键论证**：
- 原则 5（§2.3）：「接口等第二个实现出现时才成型」。进程外传输的接口形状（JSON vs 二进制、推送 vs 拉取、按房间/用户/类型过滤、顺序要求、断线语义、unix socket vs TCP）**全部依赖第一个消费者的真实需求**——现在定任何一个都是猜。
- 拉模型已被证明够用：`/rooms` 端点证明"非实时消费者 = 事件维护快照 + HTTP 拉取"零新增机制。
- 实时推送类需求（触摸流回放）是唯一可能逼出进程外传输的，但它连"进程内 Observer"都还没实现（阶段 4 前置），进程外更远。

## 决策

1. **不设计"进程外事件传输协议"**（序列化格式/传输/过滤/重连）——等第一个明确的外部消费者出现，以它的真实需求设计（原则 5）。
2. **接缝层保持现状，不动**：`EventSink` + `CompositeSink` + 组合根注入已覆盖"任意数量进程内消费者"；未来进程外消费者 = **实现一个 `EventSink` 的传输层**（unix socket/TCP 推送或快照拉取），与房间 impl、SessionSink 同级，**不需要动契约、不动 core**。
3. **本 ADR 作为触发条件清单**（见下），防止未来在无消费者时"为设计而设计"。

### 触发条件清单（何时该设计进程外协议）

同时满足以下三条才启动协议设计：

1. 出现第一个**明确的**外部消费者需求（回放录制进程、管理面板实时视图、统计管道、Webhook 任一立项）；
2. 且该消费者**不满足于拉模型**（`/rooms` 式快照轮询不够，需要实时事件流或触摸流）；
3. 设计输入齐全：事件范围（全量/按房间/按类型）、粒度（原始事件 vs 聚合）、顺序要求（严格有序 vs 最终一致）、断线语义（丢帧可接受 vs 必须补发）、传输约束（unix socket / TCP / 共享内存）。

任一条件不满足 → 用拉模型或进程内 Observer 解决，不动内核。

## 后果

- 正面：不猜第二个实现的接口（原则 5）；内核保持纯（事件出口零代码 = 零内存、零维护）；未来进程外消费者 = 一个 `EventSink` 实现 + 组合根注册，改动量与 RoomListSink 同级；契约测试套件（phira-contract）未来可直接泛型覆盖"任何 EventSink 实现"的可测试性。
- 负面：第一个外部消费者出现时需现场设计协议（一次性成本，正当成本）；若未来有"严格有序 + 补发"类需求（如审计），需要额外机制（顺序号/游标）——但那是真实需求驱动的，非现在能猜。

## 替代方案

- **现在就设计完整进程外订阅协议**（JSON over TCP + 过滤 + 重连 + 游标）——被拒：违反原则 5（猜接口）；无消费者的协议 = 死代码 + 维护税；设计出的形状（序列化格式/过滤粒度）大概率与第一个真实消费者不符。
- **Redis pub/sub 做事件出口**——被拒：为单一未来需求引入外部依赖（无外部组件约束，见此前"是否引入 Redis"讨论）；unix socket 直连比 Redis 更轻（微秒级 vs 网络往返）；Redis 的价值在多实例共享，单实例进程外消费用不上。
- **事件写日志文件供外部轮询**——被拒：日志不是事件流（无结构化、无过滤、无顺序保证、轮询延迟大）；日志是运维面，事件是业务面，混用会互相污染（token 不落日志红线 §11）。
- **gooophira 式 Agent 进程形态（现在就搭扩展进程框架）**——被拒：那是"应用层部署形态"而非"内核接口"；先有消费者再谈形态；Agent 框架本身也是猜需求（飞书/分享站/统计的接口在消费者出现前不可知）。
